# 스펙: 주간보고 (2026-07-10)

## 개요
개인이 자기 SR을 골라 주간보고 등록(정확한 반영예정일 + SR 예정일과 다르면 지연사유 필수) → 업무리더(02)가 파트원 보고에 의견/수정 후 파트 취합 최종본 제출 → 팀장(01)/ADMIN이 부서 파트별 취합본 조회·최종의견. 패키지 `com.meritz.dash.weekly`.

## 주차 키
- `WEEK_YMD VARCHAR2(8)` = 해당 주 **월요일** YYYYMMDD.
- 클라이언트가 아무 날짜나 보내면 서버가 그 날짜가 속한 ISO 주의 월요일로 **정규화**(예: 20260712(일)→20260706). 형식 오류/실존하지 않는 날짜는 400.

## DDL — `V021__create_weekly_report_tables.sql` (번호 고정, 19c 호환만)
```sql
CREATE TABLE DASH_WKLY_RPT (
    RPT_ID        NUMBER GENERATED BY DEFAULT AS IDENTITY,
    WEEK_YMD      VARCHAR2(8)    NOT NULL,          -- 주 시작(월) YYYYMMDD
    SR_NO         VARCHAR2(30)   NOT NULL,          -- 기간계 SR번호
    SR_TITL       VARCHAR2(500),                    -- SR 제목 스냅샷(TITL_CNTT)
    REG_EMPNO     VARCHAR2(30)   NOT NULL,          -- 작성자
    DEPT_CD       VARCHAR2(20),                     -- 작성 시점 소속 스냅샷
    PART_CD       VARCHAR2(20),
    RPT_CNTT      VARCHAR2(2000) NOT NULL,          -- 개인 의견/내용
    PLAN_DATE     VARCHAR2(8)    NOT NULL,          -- 개인이 적은 반영예정일 YYYYMMDD
    SR_PLAN_DATE  VARCHAR2(8),                      -- SR 반영예정일(RFLC_SCDL_DATE) 스냅샷
    DELAY_RSN     VARCHAR2(1000),                   -- 지연사유
    LEADER_CMT    VARCHAR2(1000),                   -- 업무리더 추가의견
    CREATED_AT    TIMESTAMP DEFAULT SYSTIMESTAMP NOT NULL,
    CREATED_BY    VARCHAR2(30),
    UPDATED_AT    TIMESTAMP,
    UPDATED_BY    VARCHAR2(30),
    CONSTRAINT PK_DASH_WKLY_RPT PRIMARY KEY (RPT_ID),
    CONSTRAINT UK_DASH_WKLY_RPT_WK_SR_EMP UNIQUE (WEEK_YMD, SR_NO, REG_EMPNO)
);
CREATE INDEX IX_DASH_WKLY_RPT_WEEK ON DASH_WKLY_RPT (WEEK_YMD);

CREATE TABLE DASH_WKLY_SUM (
    SUM_ID        NUMBER GENERATED BY DEFAULT AS IDENTITY,
    WEEK_YMD      VARCHAR2(8)    NOT NULL,
    DEPT_CD       VARCHAR2(20)   NOT NULL,
    PART_CD       VARCHAR2(20)   NOT NULL,
    SUM_CNTT      VARCHAR2(4000) NOT NULL,          -- 파트 취합 최종본
    REG_EMPNO     VARCHAR2(30)   NOT NULL,          -- 제출한 업무리더
    TEAM_CMT      VARCHAR2(1000),                   -- 팀장 최종의견
    TEAM_CMT_EMPNO VARCHAR2(30),
    CREATED_AT    TIMESTAMP DEFAULT SYSTIMESTAMP NOT NULL,
    CREATED_BY    VARCHAR2(30),
    UPDATED_AT    TIMESTAMP,
    UPDATED_BY    VARCHAR2(30),
    CONSTRAINT PK_DASH_WKLY_SUM PRIMARY KEY (SUM_ID),
    CONSTRAINT UK_DASH_WKLY_SUM_WK_PART UNIQUE (WEEK_YMD, DEPT_CD, PART_CD)
);
```

## API (전부 `/api/v1`, envelope `ApiResponse.of`)

### 개인 보고
| Method | Path | 권한 | 비고 |
|---|---|---|---|
| POST | `/weekly-reports` | 인증자 전원 | JSON `{week, srNo, content, planDate, delayReason?}`. 201 |
| GET | `/weekly-reports?week=` | 스코프 조회 | **03=본인 / 02=본인 파트 / 01=본인 부서 / ADMIN=전체(dept/part 파라미터 드릴다운)**. week 필수 |
| GET | `/weekly-reports/{id}` | 스코프 내 | 스코프 밖 403(fail-closed), 미존재 404 |
| PUT | `/weekly-reports/{id}` | 작성자 / 같은 파트 02 / ADMIN | `{content?, planDate?, delayReason?}` 부분수정. planDate 변경 시 지연사유 규칙 재검증 |
| PUT | `/weekly-reports/{id}/leader-comment` | `@Auth(roles={"02","01","ADMIN"})` | `{comment}`. 02=같은 dept+part만, 01=같은 dept만, ADMIN=전체. 아니면 403 |
| DELETE | `/weekly-reports/{id}` | 작성자 또는 ADMIN | 204 |

### 파트 취합본
| Method | Path | 권한 | 비고 |
|---|---|---|---|
| POST | `/weekly-summaries` | `@Auth(roles={"02","ADMIN"})` | `{week, content, deptCd?, partCd?}`. 02=본인 dept/part 강제(파라미터 무시), ADMIN=dept/part 필수. (week,dept,part) **MERGE upsert** — 신규 201, 갱신 200 |
| GET | `/weekly-summaries?week=` | 스코프 조회 | 03/02=본인 파트, 01=본인 부서(파트별 목록), ADMIN=전체(dept 드릴다운) |
| PUT | `/weekly-summaries/{id}/final-comment` | `@Auth(roles={"01","ADMIN"})` | `{comment}` → TEAM_CMT/TEAM_CMT_EMPNO. 01=본인 부서 것만(아니면 403) |

## 비즈니스 규칙 (테스트로 고정 — 경계값)
1. **지연사유 규칙**: 등록/수정 시 기간계에서 해당 SR의 반영예정일(`RFLC_SCDL_DATE`)을 실시간 조회해 `SR_PLAN_DATE` 스냅샷 저장.
   - `planDate != srPlanDate`(둘 다 존재) && `delayReason` 공백 → **400**.
   - `planDate == srPlanDate` → delayReason 선택.
   - `srPlanDate` null(SR에 예정일 없음) → delayReason 선택.
2. SR이 기간계에 존재하지 않으면 400(`IllegalArgumentException`, "SR 없음").
3. (week, srNo, 작성자) 중복 등록 → **409**(`DuplicateKeyException` → 매퍼 selectExists 선검사 후 `IllegalStateException`→409 매핑은 기존 핸들러에 없음 — **선검사 후 409는 `ResponseStatusException(CONFLICT)` 대신 기존 패턴 확인, 없으면 서비스에서 선검사 후 `IllegalStateException` 던지고 컨트롤러단 처리 금지·GlobalExceptionHandler 수정 금지 → 가장 단순하게: 서비스 선검사 후 커스텀 `ConflictException`을 weekly 패키지에 만들고 `@ResponseStatus(HttpStatus.CONFLICT)` 붙이기**).
4. DEPT_CD/PART_CD 스냅샷 = 등록 시점 `AuthContext.deptCd()/partCd()`. RBAC은 저장된 스냅샷 기준 비교(fail-closed: 소속 null인 비ADMIN은 본인 것만).
5. week 정규화: 임의 날짜 → 그 주 월요일. 20260712(일)→20260706. 비날짜/형식오류 400.

## 변경(2026-07-13)

사용자 정책 변경 2건 반영(위 본문의 해당 규칙은 이 섹션이 우선한다).

### 1. 지연사유 필수 해제 — 항상 선택
- `delayReason` 은 등록/수정 어떤 경우에도 **선택값**. `planDate != SR_PLAN_DATE`(둘 다 존재)여도 사유 없이 저장 허용(기존 400 폐지).
- 유지: SR_PLAN_DATE 스냅샷 저장(수정 시 planDate 변경이면 재조회), SR 미존재 400, planDate STRICT YYYYMMDD 형식검증 400.

### 2. 파트당 주간 취합본 여러 건 허용
- `V022__allow_multiple_weekly_summaries.sql`: `UK_DASH_WKLY_SUM_WK_PART` 제거, 조회용 비유니크 인덱스 `IX_DASH_WKLY_SUM_WK_PART(WEEK_YMD, DEPT_CD, PART_CD)` 생성.
- `POST /weekly-summaries`: MERGE upsert 폐지 → **항상 신규 INSERT(201)**. 매퍼 `insertSummary`(useGeneratedKeys 로 SUM_ID 회수). 02=본인 dept/part 강제, ADMIN=dept/part 필수(400), 그 외 403 은 기존 그대로. existsSummary/mergeSummary/created 플래그/409 변환 제거.
- `PUT /weekly-summaries/{id}` 신설: `{content}` 로 본문(SUM_CNTT)만 수정 — TEAM_CMT 는 변경하지 않음. 같은 dept+part 의 02 또는 ADMIN(fail-closed, 그 외 403), 미존재 404.
- `DELETE /weekly-summaries/{id}` 신설: 같은 권한 → 204.
- GET 목록 스코프 동일, 한 파트에 여러 행 반환 가능(정렬 `DEPT_CD, PART_CD, SUM_ID DESC`). final-comment 는 행 단위 그대로.
- 개인 보고(DASH_WKLY_RPT)의 UK(주·SR·작성자)·409 는 변경 없음(`ConflictException` 은 개인 보고에서 계속 사용).

## 변경(2026-07-13) 취합본 보고 선택

업무리더가 파트원 개인 보고를 조회해 **선택하면 그 선택된 보고들이 파트 취합본을 구성**하는 모델 추가.

### 데이터 모델
- `V023__create_weekly_summary_report_link.sql`: 링크 테이블 `DASH_WKLY_SUM_RPT(SUM_ID, RPT_ID)` — 복합 PK,
  양쪽 FK 모두 `ON DELETE CASCADE`(취합본/개인 보고 삭제 시 링크 자동 정리, 애플리케이션 코드 불필요 — IT 로 검증),
  역방향 조회용 `IX_DASH_WKLY_SUM_RPT_RPT(RPT_ID)`. V021/V022 는 수정하지 않음(19c 호환).

### API
- `POST /weekly-summaries` 바디에 `rptIds`(선택, number 배열) 추가: `{week, content, rptIds?, deptCd?, partCd?}`.
  각 rptId 는 ①DASH_WKLY_RPT 존재 ②WEEK_YMD == 정규화된 week ③DEPT_CD+PART_CD == 취합본 대상 dept/part
  (02=본인 소속, ADMIN=지정값) 을 모두 만족해야 하며 하나라도 실패하면 400(전체 거부, summary INSERT 없음).
  통과 시 summary INSERT 후 링크 일괄 INSERT. `rptIds` 없거나 빈 배열이면 링크 없이 기존과 동일.
- `PUT /weekly-summaries/{id}` 바디 `{content?, rptIds?}`: `rptIds` 가 오면(빈 배열 포함) **기존 링크 전부
  삭제 후 교체**(동일 검증 — 검증 실패 시 400·기존 링크 보존), null 이면 링크 불변. `content` 는 null 이면
  본문 불변, 값이 오면 기존 로직 그대로 SUM_CNTT 수정(blank 400). 둘 다 null 이면 400.
- `GET /weekly-summaries?week=` 각 취합본에 선택 보고 임베드:
  `"reports": [{rptId, srNo, srTitl, regEmpno, rptCntt, planDate, srPlanDate, delayRsn, leaderCmt}]`
  (RPT_ID 오름차순, 없으면 빈 배열). N+1 금지 — sumId 목록으로 링크⨝보고 한 방 쿼리(foreach IN) 후
  서비스에서 그룹핑. 등록/수정/final-comment 단건 응답에도 동일하게 임베드.
- 권한/스코프/final-comment/삭제 규칙은 기존 그대로.

### 구현
- 매퍼(`WeeklyReportMapper` + XML) 추가: `insertSummaryReports(sumId, rptIds)`(INSERT SELECT — 중복 rptId
  자연 dedup), `deleteSummaryReports(sumId)`, `selectReportsForValidation(rptIds)`,
  `selectSummaryReports(sumIds)`. 전부 `#{}`/foreach 바인딩.
- DTO: `WeeklySummary` record 에 `reports`(중첩 `Report` record) 추가 — 8-인자 편의 생성자로 기존 호출부 호환.
  매퍼 로우용 `WeeklyReportKey`, `WeeklySummaryReportRow` 신설.
